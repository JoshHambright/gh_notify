# gh_notify v1.2: install & update, settings, sounds, filters, generic workflows

Status: approved scope (2026-10-14). Builds on v1 and v1.1 specs in this folder.

## 0. Goals

1. **Installable and self-updating.** A per-user installer, quiet auto-update from GitHub
   Releases, CI with quality gates, a tag-triggered release, and real install/upgrade/uninstall tests.
2. **Settings window.** A visual editor for everything in `config.json`. Raw JSON stays available.
3. **Sounds.** Per-rule sounds (built-in set or custom .wav) and per-rule off-hours alerting.
4. **Filters.** Mute (no toast/sound/auto-agent) and hide, by org/project/repo, plus timed
   "Mute this repo/org" from a row.
5. **Generic workflows.** Built-in `review` / `diagnose-ci` prompts that need no skills; the user's
   skills become opt-in; `command` profiles run any CLI or script.
6. **Clear tray icon.** No red when nothing is waiting; red sweep + red count when something is.
7. **Docs.** A README with badges, screenshots, quickstart and FAQ, plus a `docs/` user guide.

Non-goals: code signing (stubbed only), macOS/Linux, a second update channel, editing agent
deny lists in the UI (shown read-only), syncing settings between machines.

Already shipped ahead of v1.2 (16bac3d): the popup no longer rebuilds row visuals on no-op
re-renders, which fixes the first chevron click after opening being swallowed.

All names in code, tests, docs, screenshots and examples are placeholders
(contoso / fabrikam / acme, alice / bob). Nothing names a real org, client, tenant or subscription.

## 1. Packaging and updates (Velopack)

- **Package.** `dotnet publish` self-contained `win-x64`, then `vpk pack` with
  `--packId GhNotify --packVersion <tag> --mainExe GhNotify.exe --icon app.ico
  --shortcuts StartMenuRoot`. The output is `GhNotify-win-Setup.exe`, a full `.nupkg`, delta
  packages and `releases.win.json`.
- **Install location.** Per user, `%LocalAppData%\GhNotify` with no admin rights. Velopack owns
  that folder and deletes it on uninstall.
- **App data moves out of the install folder.** Today state, logs, worktrees, scratch and the toast
  logo live in `%LocalAppData%\GhNotify`, the same folder Velopack owns. v1.2 moves them to
  `%LocalAppData%\GhNotify-data\`. Config stays at `%APPDATA%\GhNotify\config.json`.
  - One-time migration at startup: if the old `state.json` exists and the new one doesn't, move
    `state.json` and the `logs` folder.
  - Existing agent worktrees are left in place. Their stored paths are absolute, so the existing
    sweep still cleans them up.
  - Overrides for tests and dev: `GHNOTIFY_CONFIG_DIR` (config) and `GHNOTIFY_DATA_DIR` (data).
- **App entry.** `VelopackApp.Build()` runs first in `Main`, before WPF starts, with these hooks:
  - after install: register the Start-menu shortcut (Velopack) and enable Start with Windows
  - after update: rewrite the Run key if it points at an old path
  - before uninstall: delete the Run key, clear our toasts from Action Center, and stop.
    Config and logs are kept (the README says how to delete them).
- **Startup path.** `StartupRegistration` writes the stable launcher path
  (`%LocalAppData%\GhNotify\current\GhNotify.exe`, confirmed by the Task 0 spike) instead of
  `Environment.ProcessPath`, when running installed. In a dev build it keeps today's behaviour.
- **UpdateService** (App):
  - Installed builds only. In a dev build it reports "Dev build — updates off".
  - Source: `GithubSource("https://github.com/JoshHambright/gh_notify", token: null, prerelease: false)`.
    The env var `GHNOTIFY_UPDATE_FEED=<dir>` swaps in a local directory source; it exists for
    the install tests.
  - Checks 30 s after launch, then every `updates.checkHours` (default 4), then on
    "Check for updates". Downloads quietly.
  - When a download finishes, the popup footer shows "Update ready · v1.2.3 · Restart" and the
    tray menu shows "Restart to update (v1.2.3)". It never restarts on its own; an exit through
    the menu applies the update via `WaitExitThenApplyUpdates`.
  - Failures (offline, rate limit) are logged and shown only in Settings › General as
    "Last check failed: …"; they never toast.
  - Config: `updates: { enabled: true, checkHours: 4 }` (checkHours 1–168).
- **Version.** The tag sets `-p:Version`. The tray tooltip, Settings › General and the
  `--version` flag show it.

## 2. CI, release and quality gates

- **`.github/workflows/ci.yml`** runs on push and PR on `windows-latest`. All gates are required:
  1. `dotnet build -c Release -warnaserror`
  2. `dotnet test` with coverlet; fails below the floor in `build/coverage-floor.txt`. The floor
     is set just below the current line coverage, and raising it is a one-line change.
  3. `dotnet format --verify-no-changes`
  4. leak scan (`build/leak-scan.ps1`): reads newline-separated terms from secret `LEAK_TERMS`
     and greps the tree case-insensitively. It fails on any hit, printing only `file:line`,
     never the term. On forks or PRs without the secret it is skipped with a notice.
  5. pack + install test (§3) using locally packed versions
- **`codeql.yml`** (C#, weekly + PR) and **`dependabot.yml`** (NuGet + Actions, weekly).
- **`release.yml`** runs on tag `v*.*.*`:
  1. the CI gates
  2. publish
  3. `vpk download github` (previous release, for deltas)
  4. `vpk pack`
  5. install test against the real previous release
  6. `vpk upload github --publish --releaseName v<ver> --tag v<ver>`
  - Release notes come from the tag annotation, else from commits since the last tag.
  - A commented `# SIGNING:` step marks where `vpk pack --signParams`/Trusted Signing goes later.
- **Branch protection** on `main` requiring the CI checks is a repo setting; it's applied
  only after the user confirms (outside this plan's code).

## 3. Install, upgrade and uninstall tests

`build/test-install.ps1 -Old <dir|release> -New <dir>`, run in CI and locally. It uses a temp
`%APPDATA%`-style config dir through `GHNOTIFY_CONFIG_DIR` (new, test/dev override) so it
never touches a real config. Each step asserts and the script exits non-zero on the first failure.

1. Silent-install the old package. Assert:
   - `current\GhNotify.exe` exists, with file version = old
   - Start-menu shortcut exists
   - the Run key points at the stable path
   - the app starts and writes "gh_notify started" to its log within 20 s
2. Write a known config file, then update to the new package using `GHNOTIFY_UPDATE_FEED`.
   Assert the version is new, the config is byte-identical, the Run key is still valid and
   the app starts.
3. Silent uninstall. Assert:
   - the install dir is gone (or holds only Velopack's removal marker)
   - the Run key is gone
   - the shortcut is gone
   - the config file still exists
4. On PR CI there is no previous release, so "old" is the same build packed as `0.0.1-ci` and
   "new" as `0.0.2-ci`.

Task 0 spike confirms the exact Velopack switches for silent install, update apply and silent
uninstall, the stable exe path, and that the Run key can live in the after-install hook.

## 4. Sounds

Config:
```json
"notifications": {
  "sounds": [
    { "match": { "kind": "ApprovalPending", "repo": "acme/*" }, "sound": "builtin:alarm", "alertOffHours": true },
    { "match": { "kind": "ReviewRequested" }, "sound": "C:\\sounds\\ding.wav" }
  ]
}
```
- **Rule matching.** `match` uses `ItemMatch` (provider, repo glob, kind, author, maxChangedLines).
  The first matching rule wins. With no matching rule, the toast uses the Windows default sound,
  as today.
- **`sound` values:**
  - `"default"`: the toast's own sound
  - `"none"`: a silent toast
  - `"builtin:<name>"`: one of `chime`, `ping`, `alert`, `alarm`, `soft`. These are original tones
    generated by `build/make-sounds.ps1`, committed as .wav files under `src/GhNotify.App/Sounds/`,
    embedded as resources, and MIT-licensed with the app.
  - an absolute `.wav` path
- **Playback.** For a builtin or file sound the toast is marked silent and the app plays the .wav
  with `SoundPlayer` (async). A missing or unreadable file falls back to the default sound and
  logs a warning once per path.
- **One sound per poll.** When a poll adds several items, only one sound plays. Priority:
  ApprovalPending > MyPrCiFailing > ReviewRequested > MyPrNeedsResponse > MyPrReadyToMerge,
  then oldest first. MyPrWaiting never toasts or plays a sound (§6b).
  Each item still gets its own toast (all silent except the one carrying the chosen sound).
- **Off-hours.** Outside work hours nothing toasts (unchanged), except items whose matched sound
  rule has `alertOffHours: true`. Those toast and play their sound.
- **Muted items** (§5) never toast or play, whatever the sound rules say.
- **Pure core.** `SoundPlan.For(added, config, inWorkHours)` returns per-item
  `(toast: bool, silentToast: bool)` plus at most one sound to play. Unit-tested;
  NotificationPolicy uses it.

## 5. Mute and hide filters

Config:
```json
"filters": { "mute": ["acme/legacy-*", "ado:contoso/platform"], "hide": ["gh:fabrikam/sandbox"] }
```
- **Pattern syntax.** An optional `gh:`/`ado:` prefix, then `/`-separated segments.
  - The pattern is matched against the item's path: GitHub `org/repo`, ADO `org/project/repo`
    (ADO pipeline approvals: `org/project/<pipeline>`).
  - `*` matches within one segment; matching is case-insensitive.
  - A pattern matches if it matches the item path's first N segments, where N is the pattern's
    segment count. So `contoso` covers a whole org and `contoso/platform` a whole project.
  - Invalid patterns (empty segment, `**`) fail config validation with a clear message.
- **Muted items** still appear in the popup, dimmed, with a 🔇 tag and tooltip
  "Muted by <pattern>". They:
  - never toast or play sounds
  - never auto-run agents (the Run button still works)
  - are left out of the badge count and the header count
- **Hidden items** are dropped from the popup, badge and toasts. They are filtered after
  reconciliation, so the reconciler and last-known state are unaffected, and unhiding brings
  them back on the next render.
- **Timed mutes.** `AppState.Mutes: [{ pattern, until }]`, with `until` null = forever (but
  "forever" from the UI goes to config, below). Expired entries are pruned on load and on
  each poll.
- **Row menu.** A `⋯` button on each row shows:
  - "Mute repo ▸ 1 hour · Until tomorrow (next work-day start) · Forever"
  - "Mute org ▸ …" (same options)
  - ADO only: "Mute project ▸ …"
  - "Forever" appends the pattern to `filters.mute` through the same save path as Settings
    (with `.bak`). Timed options go to state.
- **Footer.** The `⋯` menu shows "Muted (n) ▸" listing active mutes with time left and "Unmute".
- **Pure core.** `Filters.Evaluate(item, config, stateMutes, now)` returns `Visible | Muted(pattern) | Hidden`.

## 5b. Snooze a single item

The user asked for this on 2026-10-14.

- **Snooze options.** The row `⋯` menu gets "Snooze ▸ 1 hour · 4 hours · Until tomorrow (next
  work-day start) · Next week (Monday work-day start) · Until it changes".
- **While snoozed** the item:
  - leaves its section, the badge and the header count
  - doesn't toast or sound
  - doesn't auto-run agents
  - has its existing toast removed from Action Center
- **"Snoozed (n)" section.** Snoozed items appear in a collapsed section at the bottom (next to
  "Waiting on others"), each with time left (or "until it changes") and **Unsnooze**.
- **Waking.** A snooze ends when:
  - its time passes
  - for "until it changes" (and any timed snooze too): the item changes. That means the
    reconciler reports it in `Changed` (new head sha, kind detail, or approval/vote state),
    including a new unresolved thread.
  - the user unsnoozes it

  On wake the item returns to its section and is announced like a new item: a toast during work
  hours (or off-hours when its sound rule says so) with title prefix "Back: ".
- **Item leaves the inbox** (merged, approved, closed): its snooze is dropped, with no toast.
- **State.** `AppState.Snoozes: [{ key, until?, untilChange }]`, pruned on each poll.
  Snoozes survive restarts.
- **Pure core.** `Snoozes.Evaluate(entries, snoozes, diff, now)` returns
  `(active snoozed keys, woken items, pruned snoozes)`. Unit-tested.
- **Snooze vs mute vs hide:**
  - snooze is one item, temporary, and comes back by itself
  - mute is a repo/org/project: still listed, but silent
  - hide is a repo/org/project, gone entirely

## 6. Generic workflows

- **New built-in profiles** (no skill required):
  - `review`: "Review the pull request at {url}. Read the diff and the surrounding code. List bugs,
    risky changes and missing tests, most important first, with file:line. Do not post, approve,
    comment or push anything. End with a 1–3 line summary starting "SUMMARY:"."
  - `diagnose-ci`: "The pull request at {url} has failing checks. Read the failing check logs and
    the relevant code, find the root cause of each failure, and suggest the smallest fix. Make no
    commits, pushes or comments. End with a 1–3 line summary starting "SUMMARY:"."
  - `peer-review` and `pr-shepherd` stay as built-ins with `requiresSkill`.
- **Defaults.** `defaultProfiles` maps item kind → profile name, overridable by rules as today.
  Built-in defaults:
  - ReviewRequested → `review`
  - MyPrCiFailing and MyPrNeedsResponse → `diagnose-ci`
  - ApprovalPending → none

  Button labels: `review`/`peer-review` → "Pre-review", `diagnose-ci`/`pr-shepherd` → "Diagnose",
  others → the profile name.
- **This user's migration.** The controller adds
  `"defaultProfiles": { "ReviewRequested": "peer-review", "MyPrCiFailing": "pr-shepherd", "MyPrNeedsResponse": "pr-shepherd" }`
  to the local config by hand (with a backup), so nothing changes for them. No code-level migration.
- **Command profiles:**
  ```json
  "agentProfiles": {
    "triage": { "command": ["pwsh", "-NoProfile", "-File", "C:\\scripts\\triage.ps1", "{url}"], "needsWorktree": false }
  }
  ```
  - A profile has exactly one of `prompt` or `command` (validation error otherwise).
  - Placeholders are filled per argument with `PromptTemplate.Fill`, and arguments go through the
    existing `ProcessRunner` quoting and the CR/LF/`"`/`%`/`!` rejection.
  - Env: `GHN_URL, GHN_REPO, GHN_NUMBER, GHN_TITLE, GHN_KIND, GHN_PROVIDER, GHN_AUTHOR, GHN_ITEM_KEY`.
  - Working dir: a worktree when `needsWorktree` is true, else the located clone, else
    `%TEMP%\GhNotify\cmd`.
  - Same coordinator concurrency, timeout, inflight and sweep rules as Claude runs.
  - Result:
    - stdout+stderr, keeping the last 64 KB
    - summary = the first line starting `SUMMARY:`, else the last non-empty line
    - exit code 0 → Ready, otherwise Failed with "exit <code>"
    - cost is blank; "Open in Claude" is hidden (no session)
  - Allowed/disallowed tools don't apply to commands; the Settings editor says so.
- **Runner seam.** `IAgentRunner` with `ClaudeRunner` and `CommandRunner`. The coordinator picks
  by profile. `AgentRun` gains `Kind: Claude|Command`.

## 6b. My PRs: ready to merge, and waiting on others

The user asked for this on 2026-10-14: an approved, green PR is waiting on its author to merge it,
and all open PRs should be visible in one place.

- **New `ItemKind` values:**
  - `MyPrReadyToMerge`: alerts like other kinds.
  - `MyPrWaiting`: informational only.
- **One "my PR" item per PR.** Precedence: `MyPrCiFailing` and `MyPrNeedsResponse` (as today; both
  may appear), else `MyPrReadyToMerge`, else `MyPrWaiting`. Drafts follow `includeDrafts` and are
  never ReadyToMerge. The keys differ per kind (`gh:ready:…`, `gh:waiting:…`, `ado:ready:…`,
  `ado:waiting:…`), so a Waiting → Ready transition is a remove plus an add, and Ready toasts.
- **GitHub ready.** All of:
  - `reviewDecision == APPROVED`
  - the rollup state is `SUCCESS`
  - `mergeStateStatus` is `CLEAN` or `HAS_HOOKS`
  - not a draft
  - not CiFailing or NeedsResponse

  `reviewDecision == null` (no review required) with green checks counts as Waiting, not Ready.
  The GraphQL query adds `mergeStateStatus`; the Task 0 spike confirms it's returned without a
  preview header.
- **ADO ready.** All of:
  - not a draft
  - `mergeStatus == succeeded`
  - no reviewer vote < 0
  - every blocking policy evaluation is `approved` or `notApplicable`
- **Waiting.** Every other open PR authored by the user that doesn't match another kind.
  - Detail text: GitHub "Waiting on review" / "Checks running"; ADO "Waiting on N reviewers".
- **Ready to merge in the UI:**
  - its own section "My PRs — ready to merge"
  - counts in the badge and header
  - toasts as "Ready to merge"
  - sound priority after MyPrNeedsResponse
  - no default agent profile and no in-app merge action. Opening the PR in the browser to merge
    is enough for v1.2.
- **Waiting in the UI:**
  - a last section, "Waiting on others (n)", collapsed by default with a toggle
  - the expanded state persists in `AppState.WaitingExpanded`
  - never toasts, never sounds, never auto-runs, never counts in the badge or header
  - filters still apply
- **Settings.** Sound/rule kind dropdowns list both new kinds. Defaults have no row for Waiting.

## 7. Settings window

A separate WPF window (`SettingsWindow`) in the H theme, following the dark/light mode, about
880×620 and resizable. It is opened from:
- the tray menu "Settings…"
- the popup `⋯` › "Settings…"
- the config-error banner ("Fix in Settings")

Only one instance exists; opening it again focuses the existing window.

**Layout.** A left nav, the page on the right, and a bottom bar with "Cancel" and "Save". Save is
disabled until something changes. Pages:

| Page | Contents |
|---|---|
| General | Poll interval; work hours (day toggles Mon–Sun, start/end time pickers); Start with Windows; theme (System/Dark/Light); updates (on/off, check interval, version, "Check now", last-check status); max concurrent agents; agent timeout. |
| Sources | GitHub: enabled, include drafts, watch repos (chip list + add). Azure DevOps: enabled, include drafts, discover orgs; orgs list = discovered ∪ configured, each with a checkbox (unchecked → `excludeOrgs`) and "Add org"; az subscription / tenant text fields with a "Test ADO sign-in" button showing ✓ or the AADSTS hint. Repo roots (folder list with Browse). Display: repo aliases (two-column table), max repo chars. |
| Notifications | Sound rules as cards: "When [kind ▾] in [repo pattern] by [author] → [sound ▾] [▶ test] [ ] alert off-hours", reorder ↑↓, delete, "+ Add sound rule". Sound dropdown: Default, None, five built-ins, "Custom file…" (file picker, .wav only). |
| Filters | Two chip lists, Muted and Hidden, with add-pattern input and live "matches N current items" hint; Timed mutes list with time left and Unmute. |
| Workflows | Defaults: one row per item kind → profile dropdown. Rules as cards: "When [kind] in [repo] by [author] ≤ [n] lines → run [profile ▾] [Auto/Button/Off]", reorder, delete, add. Profiles: list (built-ins read-only, with "Duplicate to edit"); profile editor has Type toggle Claude prompt / Command, prompt multiline box with placeholder chips, or command args list; needs worktree; requires skill (with ✓/✗ installed); allowed/disallowed tools (read-only info for built-ins). Hooks: event ▾ + match + command args, add/delete. |
| Advanced | Open config.json; Open logs folder; Open state folder; config path; "Reset to defaults…" (two-step, writes backup). |

- **Draft model.** Opening the window deep-clones the current config into a `SettingsDraft`
  (Core, via a JSON round-trip). Pages bind to the draft.
- **Save:**
  1. `ConfigStore.Validate(draft)`. Errors are shown inline on the owning page and the nav item
     gets a red dot; nothing is written.
  2. `ConfigStore.Save(config)` writes `config.json.bak`, then writes atomically (temp + replace)
     with the same serializer options as load (camelCase, string enums, indented).
  3. Reload, then the window closes.
- **Cancel or close with changes** asks "Discard changes?" inline in the bottom bar, not as a
  modal dialog.
- **External edits.** If `config.json` changed on disk while the window was open (mtime/hash
  differs from when it was opened), Save shows "config.json changed outside Settings —
  Reload / Overwrite".
- **Comments.** The first Save of a file containing JSON comments shows once: "Saving rewrites
  config.json and drops comments. A backup is kept as config.json.bak." Unknown properties are
  preserved via `[JsonExtensionData]` on `AppConfig`.
- **Testable core.** `SettingsDraft` (Core) exposes:
  - rule/sound/profile list operations (add, remove, move)
  - `Summary(rule)` sentences
  - `Validate()` → errors keyed by page + field
  - `IsDirty`

  These are unit-tested. The WPF pages are thin bindings over it.
- **Preview.** `--render-preview` adds `settings-<page>-dark/light.png` for each page using sample data.

## 12. Review focus (risks)

1. Uninstall leaving a Run key → the app can't start at login and Windows shows an error each boot.
2. A Settings save racing an external edit or a hot reload → lost edits (§7 conflict check).
3. Hidden filters must not stop reconciliation → otherwise items reappear stale or toast again
   after unhide.
4. A command profile with user-controlled placeholders (PR title) → must stay one argument each,
   never shell-interpreted.
5. Update applied while an agent run is in flight → the run is lost; restarting to update waits
   for running agents (or the restart confirm says "2 agents running — restart anyway?").
