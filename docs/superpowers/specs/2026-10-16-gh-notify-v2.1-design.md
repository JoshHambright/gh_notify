# gh_notify v2.1: macOS

Status: approved design (2026-10-16), updated during implementation (see "Changed during implementation" at the end). Builds on v2.0. Roadmap: `docs/roadmap.md` (v2.1), issue #1.

## 0. Goals

1. Run the v2.0 app on **macOS** as a menu-bar app, with the same features as Windows, on Apple Silicon and Intel.
2. **No change on Windows.** The Windows build, tests, installer and update channel stay exactly as they are.
3. Install, update and uninstall on macOS through Velopack, verified in CI on `macos-latest`, with a final smoke test on a
   real Mac.

Non-goals:
- notification action buttons (Windows toasts are click-to-open; macOS matches that)
- Developer ID signing and notarization (the app is ad-hoc signed)
- an uninstaller on macOS (documented manual steps instead)
- new features or visual changes

Names in code, tests, docs and screenshots are placeholders only (contoso / fabrikam / acme, alice / bob).

### What round 1 showed

`build/mac-test.sh` on macOS 27.0.1, arm64, .NET 10.0.402, at `feat/v2.0`:
- The build succeeds and all 212 UI tests pass.
- The screenshots match Windows: fonts, glyphs (⋯, chevrons) and colours are all correct.
- 774 of 785 Core tests pass. All 11 failures are tests that assume Windows (`cmd`, `findstr`, `.cmd` scripts,
  `C:\` paths), not product bugs.

## 1. Project layout

| Project | Target | Contents |
|---|---|---|
| `native/mac/` (new) | Swift, macOS 13+ | `GhNotifyMac.swift` (about 300 lines) and `build.sh`. Builds `libGhNotifyMac.dylib`, universal (arm64 + x86_64), with `swiftc`. Exposes a plain C API (`@_cdecl`) |
| `GhNotify.Platform.Mac` (new) | `net10.0` | The macOS implementations of the six platform interfaces (§2). Calls the shim with `[LibraryImport]`. Includes the dylib when it exists, so the project also builds on Windows without it |
| `GhNotify.App.Mac` (new) | `net10.0`, RIDs `osx-arm64`, `osx-x64` | The macOS host (§3) |
| `GhNotify.App` | unchanged | The Windows host |
| `tests/GhNotify.Platform.Mac.Tests` (new) | `net10.0` | macOS-only tests. They are skipped (not failed) on other OSes |

- `VelopackUpdateClient.cs` and `AppVersion.cs` are platform-neutral. `GhNotify.App.Mac` links the same files
  (`<Compile Include="..\GhNotify.App\…" Link=…/>`) instead of copying them.
- `GhNotify.slnx` includes the new projects. On Windows, `dotnet build GhNotify.slnx` builds them without the shim.

## 2. macOS platform services (`GhNotify.Platform.Mac`)

### Shim C API

All strings are UTF-8, and the functions return 0 on success. Callbacks are unmanaged function pointers
(`[UnmanagedCallersOnly]`).

```
int  ghn_version(void);                      // shim API version; C# checks it on load
int  ghn_notify_init(void (*on_click)(const char* tag, const char* url));   // sets the delegate, requests permission
int  ghn_notify_show(const char* tag, const char* title, const char* body, const char* url, int silent);
void ghn_notify_remove(const char* tag);
void ghn_notify_clear_all(void);
int  ghn_hotkey_register(uint32_t keycode, uint32_t modifiers, void (*on_pressed)(void));  // Carbon RegisterEventHotKey
void ghn_hotkey_unregister(void);
int  ghn_login_item_status(void);             // SMAppService.mainApp: 0 off, 1 on, 2 requires approval, <0 error
int  ghn_login_item_set(int enabled);
```

Callbacks are posted to the UI thread on the C# side. The shim never calls into managed code while holding a lock.

### Services

| Interface | macOS version |
|---|---|
| `INotifier` | `MacNotifier`. The notification id is the tag, so `Remove` and `ClearAll` work. The URL goes in `userInfo`. A click becomes `Activated(tag, url is null ? "open" : ToastActions.ForUrl(url))`. Clicks that arrive before a handler is subscribed are queued and replayed, as `ToastNotifier` does. If permission is denied, that is logged once, and showing a notification does nothing. `Silent` maps to no sound in the content |
| `IHotkeyService` | `MacHotkeyService`. Maps Win/Cmd → `cmdKey`, Alt/Option → `optionKey`, Ctrl → `controlKey`, Shift → `shiftKey`, and the key name to a virtual keycode (a table for letters, digits and F1–F12). Carbon reports `eventHotKeyExistsErr` only for a clash inside gh_notify; a clash with another app usually registers anyway, so Settings can't warn about it on macOS |
| `IStartupService` | `MacStartupService` uses `SMAppService.mainApp` through the shim. `IsEnabled` is true for status 1. When the status is "requires approval", the error is logged and Settings shows "Approve gh_notify in System Settings → General → Login Items" |
| `ISoundService` | `MacSoundService`: `afplay <path>` as a detached process. The built-in ids resolve to the bundled wavs (the same files as Windows) |
| `ISystemTheme` | `AvaloniaSystemTheme`: `Application.PlatformSettings.GetColorValues().ThemeVariant` and `ColorValuesChanged`. It is platform-neutral, so it lives in `GhNotify.UI` |
| `IShell` | `MacShell`. `OpenUrl` runs `open <https url>`, `OpenFolder` runs `open <path>`, and `OpenTerminal` follows `display.terminal` (§4) |

If the shim fails to load (`DllNotFoundException`, or `EntryPointNotFoundException` when the shim is a different version),
`Composition` swaps in no-op notifier, hotkey and startup services. They log the reason once, and the app still runs.

### Menu-bar icon and popup

- Avalonia `TrayIcon`, with the existing icon renderer. The calm icon is a monochrome **template image**
  (`MacOS.IsTemplateIcon`), so macOS tints it for light and dark menu bars. The "waiting" icon is the full-colour red one.
- On Windows, clicking the icon opens the popup. On macOS, Avalonia's status item can only show a menu (it raises no
  click), so a click opens the tray menu, whose first item is **Open**. The menu is otherwise the same as on Windows.
- `PopupWindow` placement: on macOS the popup opens below the menu bar, at the top right of the primary screen's working area (§12: under the icon)
  (a tray click carries no pointer position to pick another screen). Windows is
  unchanged.

## 3. macOS host (`GhNotify.App.Mac`)

- `Program.Main`:
  - Runs `VelopackApp.Build().Run()`, with no install hooks on macOS.
  - `--version` prints the version, `--write-iconset <dir>` writes the app icon at every iconset size (§5), and the hidden
    `--test-notification` shows one sample notification shortly after startup (§7).
  - Single instance: an exclusive `FileStream` lock on `<DataDir>/instance.lock`. A second launch exits 0.
  - Then `Composition.Build()` and the Avalonia app, as on Windows.
- Paths (`MacPaths`). The `GHNOTIFY_CONFIG_DIR` and `GHNOTIFY_DATA_DIR` overrides still work:
  - config: `~/Library/Application Support/GhNotify/config.json`
  - data (state, worktrees, scratch): `~/Library/Application Support/GhNotify-data`
  - logs: `~/Library/Logs/GhNotify`
- `Info.plist` (through vpk): `LSUIElement = true` (no Dock icon), `CFBundleIdentifier = com.joshhambright.ghnotify`,
  `LSMinimumSystemVersion = 13.0`.
- Startup failure: the error is logged, and a system alert (`osascript display alert`) shows the message and the log path,
  in place of `MessageBoxW` (the Avalonia app has already exited by then).
- **PATH:** apps launched from Finder or as a login item get a minimal PATH, so `gh`, `az` and `claude` from Homebrew
  would not be found.
  - Before composition, `LoginShellPath.Merge()` runs `$SHELL -l -c 'printenv PATH'` (fish-safe) (falling back to `/bin/zsh`)
    with a 3-second timeout.
  - The entries it finds go after the current PATH, without duplicates, followed by `/opt/homebrew/bin` and
    `/usr/local/bin` if they exist.
  - A failure is logged and leaves PATH unchanged.

## 4. Core and config changes

- **Hotkey:** `HotkeyParser` accepts `Cmd` and `Command` as aliases of `Win`, and `Option` and `Opt` as aliases of `Alt`.
  On macOS, `Hotkey.ToString()` prints `Cmd` and `Option`. The default `hotkey` depends on the platform:
  `Win+Shift+G` on Windows and `Ctrl+Option+G` on macOS (Cmd+Shift+G is Finder's Go to Folder). An existing config
  value is kept.
- **Terminal:** a new `display.terminal` setting, a string, default `"terminal"`. Windows ignores it.
  - `"terminal"`: `osascript` tells Terminal.app to `do script "cd <dir> && <cmd>"`.
  - `"iterm"`: `osascript` tells iTerm2 to create a window with the default profile and write the same text.
  - Any other value is a custom command. It is run with the working directory and the command line as two arguments,
    for example `"/usr/local/bin/wezterm-open"`.
  - Every value is shell-quoted (`'…'` with `'\''` for embedded quotes) before it goes into the script line. The
    AppleScript string escapes `\` and `"`. The validator rejects an empty value.
  - Settings › Advanced shows the setting on macOS only.
- **Tests:** the Windows-only Core and Agents tests get `[WindowsFact]` / `[WindowsTheory]`, which skip on other OSes.
  `ConfigValidatorTests` and `SettingsDraftTests` use a path that is rooted on each OS (`Path.GetTempPath()`-based) in
  place of `C:\sounds\ding.wav`.
- `CommandResolver` already runs commands directly (no `cmd.exe`) on non-Windows, and `AppConfig.DefaultRepoRoot` already
  handles macOS. They need no change.

## 5. Packaging and release

- `build/pack-mac.sh <version> <outdir> [<rid>…]`, for each RID (default both):
  1. `native/mac/build.sh`: the universal dylib, built once.
  2. Self-contained `dotnet publish src/GhNotify.App.Mac -c Release -r <rid> -p:Version=<version>`, with the dylib
     copied next to the executable.
  3. `GhNotify --write-iconset` renders the app icon at every iconset size, then `iconutil` turns it into `GhNotify.icns`.
  4. `vpk pack` with `--packId GhNotify`, `--mainExe GhNotify`, `--icon GhNotify.icns`,
     `--bundleId com.joshhambright.ghnotify`, `--channel <rid>` and an `Info.plist` with `LSUIElement`. It is ad-hoc
     signed (vpk's default when no signing identity is given; the plan checks this, and `codesign -s -` is the
     fallback).
- Channels `osx-arm64` and `osx-x64` produce `releases.osx-arm64.json` and `releases.osx-x64.json`. Windows keeps its
  default `win` channel. `VelopackUpdateClient` needs no change: Velopack picks the channel from the installed package.
- `release.yml` packs Windows (`release`) and then macOS (`release-mac`, on `macos-latest`, with the notes the Windows job
  wrote), and only then publishes (`publish`):
  - `release-mac` packs both RIDs, downloading the previous release's `osx-*` files for deltas when they exist, and runs
    `build/test-install-mac.sh` from the previous macOS release on arm64 when there is one.
  - `publish` uploads Windows and both macOS channels to the same GitHub release, then writes the body once.
  - The first macOS release has no previous release, so it is a full package only.
- `release-notes.ps1` is unchanged. The same notes go into the macOS packages (`--releaseNotes`).

## 6. CI

A new `mac` job in `ci.yml`, on `macos-latest`, runs on every push and PR:

1. `native/mac/build.sh`.
2. Build Core, UI, `GhNotify.Platform.Mac`, `GhNotify.App.Mac` and the test projects with `-warnaserror`. The Windows-only
   projects are left out.
3. Run `GhNotify.Tests`, `GhNotify.UI.Tests` and `GhNotify.Platform.Mac.Tests`.
4. `build/pack-mac.sh 0.0.1-ci` and `0.0.2-ci` for arm64, then run `build/test-install-mac.sh` on them:
   - install the old `.pkg` (`sudo installer -pkg … -target /`) and check `--version`;
   - launch it, wait for the log line "gh_notify started", and quit;
   - seed `config.json` and `state.json`, apply the new package through Velopack's updater, and check the version
     changed and both files are byte-identical;
   - uninstall (remove the app, the data folders and the login item) and check nothing is left.
5. Upload the `0.0.2-ci` `.pkg` as a run artifact named `gh_notify-macos-arm64` for the tester.

The existing `ui-linux` job stays as it is. Coverage stays on the Windows job. The Mac projects are not excluded: their tests use a fake shim and run on Windows,
and total coverage stays well above the floor (88% at the first Mac PR).

`GhNotify.Platform.Mac.Tests` covers:
- the shim loads, and its version matches;
- hotkey register and unregister (real shim), and the error mapping (fake shim);
- the login-item status call returns without error;
- `MacNotifier` click translation and replay (with a fake shim);
- the `LoginShellPath` merge (PATH strings in, merged PATH out; timeout);
- terminal command quoting for each `display.terminal` mode, including quotes, spaces, `$` and backslashes;
- the keycode table.

## 7. Tester round 2

- `build/mac-test.sh --round 2 <path-to.pkg>`:
  1. installs the package;
  2. launches it with `GHNOTIFY_CONFIG_DIR` and `GHNOTIFY_DATA_DIR` pointed at scratch folders and a sample config with
     GitHub and ADO disabled;
  3. prints a checklist for the tester to answer y/n with an optional note;
  4. zips the answers, the logs (home paths replaced with `~`) and `summary.json`, like round 1.
- The checklist:
  1. menu-bar icon visible, calm and tinted correctly in light and dark;
  2. the popup opens under the icon;
  3. a test notification (`--test-notification`, a hidden flag) appears after the permission prompt;
  4. clicking it opens the popup;
  5. the hotkey toggles the popup;
  6. start at login, on and off;
  7. the theme follows System Settings;
  8. Open folder and a terminal action work;
  9. Quit from the menu.
- `docs/macos-testing.md` gains a Round 2 section: how to download the artifact from the PR's checks, the one-time
  "Open Anyway", and the steps.

## 9. Delivery

One branch, `feat/v2.1`, and one PR, like earlier releases. Each push gives the tester a fresh artifact. The PR merges

## 10. Exit criteria

- CI is green on Windows, Linux and macOS, including the macOS install, upgrade and uninstall test.
- Tester round 2 passes on a real Apple Silicon Mac.
- The Windows install test and the upgrade from the published v2.0.x still pass.
- Intel builds and passes CI. It is not smoke-tested on hardware, and the release notes say so.

## 11. Review focus (risks)

1. **Ad-hoc signing and notifications:** `UNUserNotificationCenter` may refuse to work, or never show the permission
   prompt, for an ad-hoc signed bundle. Round 2 tests this first. The fallback is to log it and stay usable without
   notifications.
2. **The login item under ad-hoc signing:** `SMAppService` may return "requires approval" or fail. The status is shown
   in Settings, not swallowed.
3. **A bad PATH from the login shell:** a slow or noisy `.zprofile` (output on stdout, prompts). Hence the timeout,
   taking only the printed value, and ignoring empty entries.
4. **Quoting in terminal actions:** a repo path or command with `'`, `"`, `$` or `\` must neither break nor inject
   into the AppleScript or shell line.
5. **Update channels getting crossed:** a Windows install must never see an `osx-*` feed, and arm64 never x64. The
   release job checks each `releases.*.json` lists only its own RID's packages.

## 12. Changed during implementation

From the final review and the first macOS CI runs:
- The macOS menu-bar icon opens its menu (Open first), not the popup: Avalonia's macOS tray icon raises no click event
  (round 2 found the icon dead without a menu) (§2).
- The popup opens on the primary screen (§2), and macOS hotkey clashes with other apps are not detectable (§2).
- `--write-iconset` instead of `--write-icns`, and a system alert for startup errors (§3).
- A custom `Info.plist` (vpk `--plist`) carries `LSUIElement`, `LSMinimumSystemVersion` and `NSAppleEventsUsageDescription`.
  Without the last one, macOS refuses the osascript calls that open terminals and never asks. Terminal failures are logged
  with a pointer to the Automation setting.
- vpk signs ad-hoc with `--signAppIdentity -`; without it only the executable is signed and the bundle does not verify.
- A `.pkg` installed with `sudo installer` leaves the bundle owned by root, so macOS updates are applied non-silently, which
  lets Velopack ask for the admin password. Round 2 records the owner a normal install leaves.
- Popup placement converts the window size with the screen's scaling (points on macOS), not the render scaling.
- Round 2 launches the app with `open`, so macOS treats it as the app bundle and asks for notification permission. It uses
  the tester's real GitHub when `gh` is signed in: disabled sources' items are retired at startup, so seeded items never
  show.
- The CI `mac` job also packs `osx-x64` (built, not run). Round 2 runs a real terminal action (`--test-terminal`).
- Round 4: the popup opens centred under the menu-bar icon. Avalonia does not expose the icon's position, so the shim (API version 2)
  finds the status item's window in the app's own windows; without it the popup falls back to the top right. Builds log and print
  (`--commit`) their git commit, the `mac` CI job builds the PR head, and round 2 refuses a package from another commit.
- The tester got no notification prompt and turned notifications on in System Settings by hand. The shim logs the permission
  status before asking, and the install guide says where to turn it on.
- Round 5: the popup opened under the icon. The hotkey registered but never fired: the shim now installs it on the event
  dispatcher target (as MASShortcut and HotKey do) instead of the application target, which Avalonia's event loop doesn't
  feed. The test notification gets a new id each run, and the shim logs the alert style and each delivery.
