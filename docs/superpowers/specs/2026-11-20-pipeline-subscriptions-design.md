# gh_notify: pipeline subscriptions (design)

Status: draft for approval (2026-11-20). Builds on v2.2. Roadmap: `docs/roadmap.md` (this is new scope; it fits the "smarter alerts" theme of v2.3).

## Intent and the why

gh_notify answers "what is waiting on me?". Today a pipeline only shows up when an approval is pending or a PR's CI is red.
The user also wants to **follow a specific pipeline**, for example "my deployment pipeline", and get a popup for the outcomes
they care about: "whenever it fails", or "only when the PROD stage fails". Pipelines they have not subscribed to stay quiet.

## Goals

1. Subscribe to a pipeline in a project (ADO Pipelines) or repo (GitHub Actions workflow), from a new **Settings › Pipelines** page.
2. Per subscription, choose which outcomes alert: **Failed**, **Succeeded**, **Partially succeeded** (ADO "succeeded with issues").
3. Per subscription, scope by **stage / environment** (e.g. `PROD*`), **branch** (e.g. `main`, `release/*`) and **only runs I triggered**.
4. A match shows a toast and a **"Pipelines" section** row in the popup. The row **stays until the user dismisses it.**
5. Everything existing keeps working on these rows: sounds rules, work-hours gating, mute/snooze/hide, hooks, `ItemMatch` rules.

## Non-goals and anti-goals

- No webhooks or service hooks (a tray app has no public endpoint). Freshness is the poll interval.
- No pipeline run controls (queue, cancel, re-run) in v1. The existing re-run action on CI-failing PR rows is untouched.
- No auto-agent or built-in profile for pipeline rows in v1. Rules and `defaultProfiles` simply have no default for the new kind.
- Not a pipeline dashboard: only subscribed pipelines, only runs that match a condition.
- Anti-goal: **a flood on day one.** Creating a subscription must not raise rows or toasts for historical runs.
- Anti-goal: a dismissed failure coming back, or a later run silently hiding an unseen failure.

## Constraints from the codebase

- Sources return `SourceResult` items; `Reconciler` diffs them per source and **removes anything the source stops returning**;
  `NotificationPlanner` toasts `Added` items; `InboxView` classifies but never removes. A pipeline run is an *event*, so the
  source must keep returning it until it is dismissed (see Lifecycle).
- State lives in `AppState` (`state.json`), config in `AppConfig` (`config.json`, unknown keys round-trip through `Extra`).
- Public repo: no mention of ATK in the app or docs. Release notes for the feature PR go in `docs/releases/vX.Y.Z.md`.
- New `ItemKind` values need handling everywhere kinds are switched on: `NotificationPolicy.TitleFor` (it throws on unknown kinds),
  `NotificationPlanner.Priority`, `InboxPresenter`/`InboxSections`, `ItemText`, `RowMenus`, `KeyMap`, `ItemMatch`, the sounds rule UI.

## Approaches considered

- **A. A pipeline source feeding the existing inbox (chosen).** A new source emits a new `ItemKind.PipelineRun`. All toast, sound,
  mute, hook and popup machinery is reused. Cost: it is only as fresh as the poll, and each subscription adds API calls.
- **B. A separate watcher with its own list and toasts.** Isolated, but duplicates toast/sound/snooze plumbing and gives the user
  two places to look. Rejected.
- **C. Webhooks or service hooks.** Instant, but needs a public endpoint. Rejected.

The user picked A and a full design doc.

## Decisions the user made

| Question | Decision |
|---|---|
| What happens to a failure in the popup? | The row stays until the user dismisses it. |
| Providers in v1 | Both GitHub Actions and ADO Pipelines. |
| Outcomes | Succeeded, Failed, Partially succeeded. |
| Scope within a pipeline | Stage/environment, branch, only runs I triggered. |
| Stage timing | With `stages` set, a stage alerts **as soon as that stage finishes**, even while the run is still going. |
| Badge | Only **failed** pipeline rows count toward the tray badge and attention state. Green rows still toast and show in the section. |

## Design

### Config

A new top-level `pipelineSubscriptions` array in `config.json` (added to `AppConfig`, validated by `ConfigValidator`):

```json
"pipelineSubscriptions": [
  {
    "id": "7f3c…",                        // stable GUID, generated by Settings
    "provider": "Ado",                     // "Ado" | "GitHub"
    "org": "acme", "project": "Platform",  // ADO; for GitHub use "repo": "acme/shop"
    "pipelineId": 42, "pipeline": "Deploy",// id is the identity; name is for display and is refreshed
    "on": ["Failed"],                      // Failed | Succeeded | PartiallySucceeded
    "stages": ["PROD*"],                   // optional globs; empty = judge the whole run
    "branches": ["main", "release/*"],     // optional globs; empty = any
    "onlyMine": false,
    "enabled": true,
    "createdAt": "2026-11-20T09:00:00Z"
  }
]
```

Globs use the same `FilterPattern` glob matching as `filters.hide`, case-insensitive.

### Item model

- `ItemKind.PipelineRun` is added at the end of the enum (persisted snapshots store kinds by name or number: the builder must
  confirm which and keep old state files loading).
- One item per **matching run** (no stages configured) or per **matching run + stage** (stages configured), so "PROD failed" and
  "QA failed" in one run are two rows. Key: `pipe:{provider}:{scope}:{pipelineId}:{runId}:{attempt}[:{stage}]`. `attempt` is GitHub's `run_attempt` or the ADO stage/build attempt, so a re-run is a new row, a re-run's success is not swallowed, and a dismissed failure never comes back through a later attempt.
- `Repo` = `org/project` (ADO) or `owner/repo` (GitHub), so existing repo-based mute/hide/match works. `Title` = pipeline name plus
  stage when scoped. `Detail` = outcome. `Details` = pipeline, run number, stage, branch, triggered by, finished at, result.
  `Url` = the run page. `UpdatedAt` = run/stage finish time. `Author` = who triggered it. `HeadSha` is the run's commit.
- Toast title by outcome: "Pipeline failed", "Pipeline succeeded", "Pipeline succeeded with issues".

### Matching rules (per subscription, per completed run)

1. Baseline: ignore anything that **finished** before `createdAt`. With no `stages`, judge a run only once it is completed. With `stages`, judge each matching stage as soon as **that stage** has a final result, even if the run is in progress, so the run list must include in-progress builds/runs.
2. `branches`: the run's source branch must match one pattern (when any are given).
3. `onlyMine`: the run's requester must be the signed-in user (ADO: `requestedFor.id` in `AdoOrgContext.MyIdentityIds`; GitHub:
   `triggering_actor.login` equals the viewer login the GitHub source already knows).
4. Outcome: with no `stages`, the run's overall result must be in `on`. With `stages`, every stage whose name matches a glob is judged
   by its own result, and each match in `on` yields a row. A stage that was skipped or never started never matches.
5. A matching cancelled run does not alert (not selectable in v1).

Provider mapping:

| | ADO Pipelines | GitHub Actions |
|---|---|---|
| Pick list | org → project → pipeline definitions (`_apis/build/definitions`) | repo → workflows (`/repos/{r}/actions/workflows`) |
| Runs | `_apis/build/builds?definitions=…&statusFilter=completed&minTime=…` | `/actions/workflows/{id}/runs?status=completed&created=>=…` |
| Stage results | build timeline, `Stage` records | the run's jobs; the **environment** comes from the Deployments API or job name (see open verification) |
| Failed | `failed` | `failure` (and `timed_out`) |
| Succeeded | `succeeded` | `success` |
| Partially succeeded | `partiallySucceeded` / stage `succeededWithIssues` | no equivalent; the option is hidden for GitHub |

### Lifecycle: row until dismissed

- The source returns, for each subscription, the freshly matched runs **plus every previously emitted, not-yet-dismissed pipeline
  item** (carried forward from the reconciler's last-known items, the same mechanism `AdoOrgSource` already uses), so a row
  does not vanish when it ages out of the API lookback or a poll fails.
- **Dismiss** is a new row action ("Dismiss", also in the ⋯ menu, with a keyboard shortcut like the other per-row keys). It writes the item key
  to `AppState.DismissedPipelineRuns` and the source stops returning that key, so the reconciler removes the row and the toast
  (the normal `Removed` path).
- Dismissed keys are pruned once their run is older than the lookback window (14 days) so state does not grow forever.
- A new run is a new key, so it is a new row and a new toast. Nothing is auto-cleared by a later green run: that is the user's choice.
- Dismissing is not mute and not snooze. Mute/snooze/hide still apply on top, and a **Dismiss all** in the section header clears the section.

### Notifications

- `Added` pipeline items go through `NotificationPlanner` like any other kind: work-hours gating, per-rule sounds, silent-when-another
  toast carries the sound. `PipelineRun` goes in `Priority` after `MyPrCiFailing`; the builder may refine ordering between outcomes
  (failures before successes).
- The first poll of a new source is an `InitialLoad` summary toast. Baselining at `createdAt` means a new subscription adds
  nothing. The builder must check that adding a subscription mid-session (source already exists) does not produce a surprise summary.
- Hooks fire `ItemAdded`/`ItemRemoved` for these items with no change to hook code; `ItemMatch.Kind` accepts `PipelineRun`.

### Polling cost and failure handling

- One request per subscription for the run list (cheap, filtered by definition and `minTime`, including in-progress builds when `stages` is set), then timeline or jobs calls only for
  *new* completed runs (or, with `stages`, runs with a not-yet-seen finished stage) that pass the branch and requester checks. Remember processed run ids per subscription in memory and in the
  carried-forward items, so each run's detail is fetched once.
- A subscription whose pipeline was deleted or whose access is gone (403/404) is reported in Settings › Pipelines as a problem and
  does not fail the whole source. Rate limits and auth failures follow the existing `SourceResult.Fail` path.
- ADO sources are per org (`ADO:{org}`) and GitHub is one source, so pipeline fetching is a separate `PipelineSource` per provider
  (named e.g. `ADO-Pipelines:{org}` and `GitHub-Pipelines`) so a pipeline problem never marks PR data stale.

### UI

- **Settings › Pipelines** (new page, between Workflows and Filters; same row/pill styling as the other pages): a list of
  subscriptions with an enable toggle and a one-line summary ("Deploy · Platform · Failed on PROD* · main"), **Add** and **Remove**.
  Add is a short flow: provider → org/project (or repo) → pipeline (searchable list) → outcomes (checkboxes) → optional stage, branch
  and "only my runs" fields, with inline validation. Edit reuses the same form.
- **Popup:** a "Pipelines" section (collapsible, like the other kind sections, with its id added to `CollapsedSections` handling) and
  a row button **Dismiss**. Row styling distinguishes failed (red), succeeded (green), succeeded-with-issues (amber), using existing theme tokens.
- Badge and tray attention count only **Normal failed** pipeline rows. Succeeded and succeeded-with-issues rows toast and appear in the section but never light the badge. Dismissed, muted and hidden rows never count.
- `docs/notifications.md`, `docs/configuration.md`, the README feature list and a `docs/releases/vX.Y.Z.md` note are updated. Screenshots
  are regenerated if `build/screenshots.ps1` covers Settings pages.

### Testing

- Core (unit): the matcher (outcomes, stages, branches, onlyMine, baseline), key generation, dismissal and carry-forward, planner
  ordering and toast titles, config validation, state load of old files without the new fields.
- ADO and GitHub clients with canned JSON (the existing test patterns), including timeline/jobs mapping and 403/404 handling.
- Headless UI tests for the Pipelines page flow, the Dismiss action and the section.
- Coverage floor in `build/coverage-floor.txt` must still pass.

## Calls made by the design author (not discussed with the user; check these)

- **Baseline** compares the run's/stage's *finish* time to `createdAt`. API queries use a wider window (one day before `createdAt`) and are filtered by finish time, so a run that started before the subscription and finishes after it does alert.
- **Carry-forward** uses the reconciler snapshot, which `state.json` persists as full `InboxItem`s (including `Details` and `Detail`), so rows survive a restart. Disabling or deleting a subscription makes its source stop returning those items, so the rows disappear through the normal `Removed` path, and its dismissed keys are pruned.
- **Restart and first poll:** restored rows are not `Added`, so no re-toast. Pipeline sources never produce an `InitialLoad` summary toast; post-baseline matches found on a source's first poll toast individually.
- **onlyMine** fails closed: if the identity is unknown (for example the GitHub viewer login could not be resolved), nothing alerts for that subscription and Settings shows a problem. ADO uses `requestedFor`; GitHub uses `triggering_actor`. Scheduled and service-triggered runs therefore do not count as "mine".
- **Several subscriptions matching one run:** one row per run (+attempt, +stage), owned by the **first matching subscription in config order**.
- **Dismissed keys** are stored as key plus the run's finish time, which is what the 14-day prune uses. Upgrade compatibility only: an older build is not required to read new state.
- **Dismiss all** clears every non-hidden pipeline row in the section, muted ones included.
- The plan may start before the GitHub spike finishes, with the stage matcher abstracted over "job name | environment"; the GitHub stage code lands after the spike.

## Open verification (a spike before the plan, recorded like `docs/superpowers/notes/2026-10-13-api-verification.md`)

1. **GitHub stage/environment.** The jobs API does not obviously expose the environment a job deployed to. Confirm whether to match
   the job name, the Deployments API (`/repos/{r}/deployments` + statuses linked to the run), or both. If neither is reliable,
   GitHub v1 scopes stages by **job name** and the UI labels the field accordingly.
2. **ADO environment vs stage.** A stage that deploys to an environment is the common PROD case. Confirm that the timeline `Stage`
   name is enough, and whether a separate environment-name match is worth adding.
3. **Permissions.** `az` token scope and the GitHub token scope must read builds/timelines/runs/deployments; confirm no new login
   or scope is needed and document it in `docs/security.md` if so.

## Left to the builder

- Exact lookback windows and the per-subscription request budget (starting points: 3-day run lookback after baseline, 14-day prune).
- Row layout and wording for the new section; the dismiss keyboard shortcut; how the Pipelines page presents provider pickers.
- Whether `PipelineSource` shares the existing `AdoClient`/`GitHubClient` instances (expected yes).
- Naming of the source types and config properties beyond what is shown above.
