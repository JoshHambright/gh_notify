# gh_notify v1.1: Emergent restyle, in-app approvals, expandable details

Date: 2026-10-13
Status: Draft, awaiting review
Builds on: `2026-10-13-gh-notify-design.md` (v1). Everything in v1 still applies
unless it is changed here.

## 1. Goals

1. **Look.** Restyle the popup in the Emergent 2025 PowerPoint template's
   visual language (direction "H"). Add dark and light themes, and replace
   the generated tray icon with the "B1" icon.
2. **Act.** Let me approve or reject deployment and pipeline approvals, and
   approve PRs, without leaving the app. Every action is a deliberate,
   two-step confirmation.
3. **See.** Each row expands to show what I'm acting on: the full agent
   summary and the context of the run or PR.

Non-goals:
- Request-changes or reject votes on PRs.
- Writing PR comments.
- Fetching plans from logs or bot comments. The plan comes only from the
  agent summary.
- Bulk actions.

## 2. Visual design (approved: direction H, icon B1)

All values come from the template theme ("Emergent Software - Dark" /
"- Light"):

| Token | Dark | Light |
|---|---|---|
| Surface | `#000C1A` | `#FFFFFF` |
| Raised (header, cards) | `#0B1A29` | `#EBF0F5` |
| Text | `#FFFFFF` | `#000C1A` |
| Muted text | `#8296AB` | `#5D7186` |
| Section label | `#9FB0C2` | `#223648` |
| Hairline | `#0F2236` | `#D8E1EB` |
| Brand red (accent, primary button, urgent edge) | `#ED352F` | `#ED352F` |
| Amber (attention) | `#F9B700` | `#F9B700` |
| Green (ready) | `#37B84D` text `#5FD474` | `#37B84D` text `#238A36` |
| Blue (links) | `#0072DA` | `#0072DA` |

**Typography.** Roboto Black for the title and the count. Roboto
Regular, Medium and Bold for everything else. The Roboto TTFs are bundled
as WPF resources (Apache-2.0, from `google/fonts`). If a font fails to
load, Segoe UI is used instead.

**Popup** (about 360 wide by 560 tall; the height grows with the
expanded row and is capped by the work area):
- **Window:** rounded 12 px corners and a soft drop shadow
  (`AllowsTransparency`, outer `Border`).
- **Header:**
  - a red circular sweep, an `Ellipse` clipped into the top-right corner
  - a small eyebrow label "gh_notify"
  - the title "Waiting on you" in Roboto Black, 17 px
  - the count in Roboto Black, 26 px
- **Light theme:** adds a 5 px red strip down the left edge, as on the
  template's light slides.
- **Section labels:** uppercase and bold, with the three-bar "E" glyph as a
  bullet (a `Path`).
- **Rows:**
  - rounded 8 px "cards" on the raised colour
  - ApprovalPending and MyPrCiFailing rows get a 3 px red inner edge on
    the left
  - layout: meta line (provider · repo · age, plus a status pill), title,
    and buttons on the right
- **Buttons:** primary actions are solid red pills. "Open in Claude" and
  other secondary actions are ghost pills.
- **Footer:** "Updated HH:mm · GitHub ✓ · ADO ✓" (a red ✗ marks an
  unhealthy source, with the problem text in its tooltip), then the icon
  buttons ↻, ☾ (theme) and ⋯ (menu).
- Opening or focusing the popup triggers a refresh (skipped if a poll finished < 10 s ago).

**Theme.**
- `ThemeMode` is System (default), Dark or Light.
- System reads
  `HKCU\Software\Microsoft\Windows\CurrentVersion\Themes\Personalize\AppsUseLightTheme`
  and follows changes live (`SystemEvents.UserPreferenceChanged`).
- The ☾ button cycles System → Dark → Light.
- The mode is persisted in `state.json` (`AppState.ThemeMode`), not in
  config.json.
- Brushes live in `Themes/Dark.xaml` and `Themes/Light.xaml` and are
  referenced with `DynamicResource`. A theme switch replaces the merged
  dictionary.

**Tray icon (B1).**
- Drawn in code (WPF `DrawingVisual` → bitmap) on a 36-unit grid:
  - a navy `#000C1A` rounded tile (rx 9)
  - a red `#ED352F` circle of radius 19 centred at (34, 2), clipped to the
    tile
  - the white git-merge glyph: main line, branch curve, two white nodes,
    and a red pending node with a white stroke
- Count badge at the top-right: none at 0 items; navy `#000C1A` with a
  white count otherwise ("99+" above 99); amber `#F9B700` with a navy
  count when any source is unhealthy or config has an error.
- The same renderer produces `app.ico` (16/24/32/48/256) for the exe icon
  and the toast app logo.

## 3. Expandable details

- Clicking a row's chevron (⌄) expands it in place, and clicking it again
  collapses it. The row title still opens the URL. Only one row is
  expanded at a time.
- The expanded panel shows, when available:
  - **Context** (all kinds):
    - provider and repo/project
    - author or initiator
    - branch → target (PRs)
    - environment name(s) and run/pipeline name (approvals)
    - head commit (short sha)
    - created/updated time
  - **Agent run** (if one exists):
    - the profile
    - the state
    - the finish time, cost and duration
    - the **full agent result text** (scrollable, monospace, up to 240 px
      tall), with "Open in Claude" and "Copy"
- To support this:
  - `AgentRun` gains `ResultText` (the full `result` from the claude JSON,
    capped at 32 KB) and `DurationSeconds`.
  - `ClaudeRunner`'s `AgentOutcome` gains `ResultText`.
- Context fields come from a new optional `InboxItem.Details`
  (`IReadOnlyDictionary<string, string>`, ordered label → value).
  Providers fill it from data they already fetch, so there are **no new
  API calls** for details. For GitHub approvals the `pending_deployments`
  response already contains the environment names. Unknown fields are
  omitted.

## 4. Actions (write operations)

### 4.1 Which actions

| Item kind | Provider | Action | API |
|---|---|---|---|
| ApprovalPending | GitHub | Approve / Reject | `POST /repos/{o}/{r}/actions/runs/{runId}/pending_deployments` with `{environment_ids:[…], state:"approved"\|"rejected", comment}` |
| ApprovalPending | ADO | Approve / Reject | `PATCH https://dev.azure.com/{org}/{project}/_apis/pipelines/approvals?api-version=7.1-preview.1` with `[{approvalId, status:"approved"\|"rejected", comment}]` |
| ReviewRequested | GitHub | Approve PR | `POST /repos/{o}/{r}/pulls/{n}/reviews` with `{event:"APPROVE", body?, commit_id:headSha}` |
| ReviewRequested | ADO | Approve PR | `PUT https://dev.azure.com/{org}/{project}/_apis/git/repositories/{repoId}/pullRequests/{id}/reviewers/{myId}?api-version=7.1` with `{vote:10}`, plus an optional comment thread when a comment is entered |

My own PRs (MyPrCiFailing, MyPrNeedsResponse) get no actions.

Agents never call these. They are app-initiated, user-confirmed calls made
with the user's own `gh`/`az` tokens. The agent deny list is unchanged.

### 4.2 Fresh check before sending

The app re-reads current state at confirm time and refuses if it changed:

- **GitHub approval:** re-GET `pending_deployments` for the run. Send only
  the environment ids that are still pending with
  `current_user_can_approve`. If there are none, show "No longer waiting
  on you" and refresh.
- **ADO approval:** GET the approval with `$expand=steps`. It must still be
  `pending`, with a pending step assigned to me or one of my groups.
- **GitHub PR:** GET the PR. It must be open, and the head SHA must equal
  the one shown in the confirm panel. If it differs: "New commits since you
  looked — refresh."
- **ADO PR:** GET the PR. It must be active, and
  `lastMergeSourceCommit.commitId` must equal the one shown.

### 4.3 Two-step confirmation (always)

1. A row's action button (`Approve…`, `Reject…`, `Approve PR…`) expands
   the row into **confirm mode**. Confirm mode shows the details panel
   (§3) plus:
   - a one-line statement of exactly what will happen:
     - "Approve deployment of acme/deploy run 9001 to **production**"
     - "Approve PR #12 in acme/api at a1b2c3d"
   - an optional comment box (single line)
   - for PR approval with no agent run, or an agent run that isn't Ready
     at the current head, a yellow warning: "No pre-review at this
     commit."
   - two buttons: **Cancel** and a red **Approve production** /
     **Approve PR**. The confirm button names the environment or PR.
2. Only the second click sends the request. The confirm button is disabled
   for 600 ms after the panel opens, so a double-click can't pass through
   both steps.
3. While sending, the row shows "Approving…". On success it shows
   "Approved ✓" (green) and a refresh is triggered. The row then
   disappears when reconciliation sees the item gone. On failure it shows
   the error inline (red) and the row stays actionable.
4. Every action is logged with the item key, the action, the outcome, and
   the comment length (not its text).

### 4.4 Code shape

- **Core:**
  - `ItemAction` enum: Approve, Reject, ApprovePr
  - `IItemActions` interface:
    - `IReadOnlyList<ItemAction> ActionsFor(InboxItem)`
    - `Task<ActionPreview> PreviewAsync(InboxItem, ItemAction, ct)`, which
      runs the fresh check and returns the statement text plus any
      warning or refusal
    - `Task<ActionResult> ExecuteAsync(InboxItem, ItemAction, ActionPreview, string? comment, ct)`
  - Records `ActionPreview(bool Allowed, string Statement, string ConfirmLabel, string? Warning, string? RefusalReason, object Token)`
    and `ActionResult(bool Ok, string? Error)`
- **GitHub:**
  - `GitHubClient` gains `PostAsync(path, body, ct)`
  - `GitHubItemActions` implements the GitHub rows of §4.1 and §4.2
- **ADO:**
  - `AdoClient` gains `SendAsync(method, url, body, ct)`
  - `AdoItemActions` implements the ADO rows
- The data needed to act is carried on `InboxItem` as new optional init
  properties:
  - `RunId` (GitHub run id)
  - `ApprovalId` (ADO)
  - `RepoId` (ADO repository id)
  - `Org` and `Project` (ADO)
  - `HeadSha` (already present)
  - The approver's ADO id comes from `AdoDirectory.GetOrgContextAsync`.
- **App:**
  - `CompositeItemActions` routes by provider
  - `InboxRow` gains `Actions` (labels), `IsExpanded`, `IsConfirming`,
    `ActionState` and `ActionMessage`
  - `PopupWindow` hosts the expand/confirm UI

## 5. Error handling

- 401/403 on an action shows "You don't have permission to approve this"
  (or the API's message) inline.
- 404/409/422 shows "This changed since you looked — refreshing" and
  triggers a refresh.
- A network or timeout error shows an inline error, and the row stays.
  Nothing is retried automatically.
- An action never runs while the item's source is unhealthy (the button is
  disabled, with a tooltip).

## 6. Testing

- **Unit tests (fakes):** for each provider action:
  - the request method, URL and body
  - fresh-check refusals: run no longer waiting, environment not
    approvable, approval already approved, PR head changed, PR closed
  - the 403 and 422 mappings
  - that `ActionsFor` is correct for each kind
- **Core:**
  - the confirm-statement text
  - the warning for an unreviewed PR or a stale agent run
  - `ResultText` capping
  - `Details` population per provider, via fixtures
- **Rendering:** `GhNotify.exe --render-preview <dir>` writes PNGs of the
  popup with sample data:
  - dark and light themes
  - collapsed and expanded rows, confirm mode, and the error state
  - the tray icon at 16/20/24/32 in the 0, 3 and attention states
  - These are reviewed visually before hand-off. A unit test checks that
    the icon renderer produces bitmaps of the requested sizes on an STA
    thread.
- **Live check, after build, with the user present:**
  - approve a real ADO or GitHub approval that the user picks, through the
    UI
  - verify the result through the API
  - nothing is ever approved without the user choosing the item

## 7. Out of scope (v1.1)

- Request changes / reject on PRs.
- Merge buttons.
- Plan extraction from logs or comments.
- Bulk approve.
- Keyboard shortcuts.
- Per-environment "skip confirm".
