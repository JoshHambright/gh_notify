# v1.2 spike notes (Task 0)

Throwaway spike. Everything below was observed on Windows 11, .NET SDK 10.0.400, on 2026-10-14.
The spike used `--packId GhNotifySpike` so it never touched the real app data. The layout is written
generically as `<packId>`; for the real app `<packId>` = `GhNotify`.

## Velopack version

- `VELOPACK_VERSION` = **1.2.161** (nuget.org, published 2026-09-29, 15 days old on 2026-10-14; newest stable at least two weeks old).
  The previous stable was 1.2.158 (2026-09-21).
- CLI: `dotnet tool install -g vpk --version 1.2.161` (installs to `%USERPROFILE%\.dotnet\tools`; needs a new shell or a PATH addition).
- Package: `<PackageReference Include="Velopack" Version="1.2.161" />`.
- `coverlet.collector` = **10.1.0** (published 2026-09-27, 17 days old; newest stable at least two weeks old).

## vpk commands

```powershell
dotnet publish src/GhNotify.App -c Release -r win-x64 --self-contained -o <pub>
vpk pack --packId <packId> --packVersion 0.0.1 --packDir <pub> --mainExe GhNotify.exe --outputDir <rel1>
vpk pack --packId <packId> --packVersion 0.0.2 --packDir <pub> --mainExe GhNotify.exe --outputDir <rel2>
```

- Output per release dir: `<packId>-<ver>-full.nupkg`, `<packId>-win-Portable.zip`, `<packId>-win-Setup.exe`,
  `RELEASES`, `releases.win.json`, `assets.win.json`. A pack takes 10-21 s; the nupkg is ~75 MB (self-contained).
- Setup file name derives from packId: `GhNotifySpike-win-Setup.exe` (so `GhNotify-win-Setup.exe` for the real app).
- `--noPortable` and `--noInst` cannot be combined. `--noInst` alone works (Portable.zip is still built).
- Useful pack options: `--shortcuts <LOC>` (default `Desktop,StartMenuRoot`), `--packTitle`, `--icon`, `--delta <MODE>`
  (default BestSpeed), `--noPortable`, `--noInst`, `--framework`, `--skipVeloAppCheck`, `--channel` (default `win`),
  `--exclude` (default `.*\.pdb`), `--aumid`.
- vpk verifies the app uses `VelopackApp.Build()...Run()`.
- The WPF csproj needs `<StartupObject>GhNotify.App.Program</StartupObject>` once a custom `Program.Main` exists
  (App.xaml otherwise generates its own `Main`; `GhNotify.App` currently has no `Program.cs`).

## Install layout / stable path

```
%LocalAppData%\<packId>\
  <packId>.exe     stub launcher (named after packId, NOT mainExe); forwards args to current\<mainExe> via Update.exe start
  Update.exe       Velopack updater / uninstaller
  current\         live app files; current\GhNotify.exe is the mainExe (name from --mainExe)
  packages\        <packId>-<ver>-full.nupkg of the installed version (+ .betaId, .velopack_lock)
```

- Stable exe path (what shortcuts point to; use this for any Run key): `%LocalAppData%\<packId>\current\GhNotify.exe`.
  It does not change across updates (verified 0.0.1 -> 0.0.4). The stub `%LocalAppData%\<packId>\<packId>.exe` also works and passes args through.
- `Update.exe` lives at `%LocalAppData%\<packId>\Update.exe`.
- Velopack logs go to `%LocalAppData%\velopack\velopack.log` and `velopack_<packId>.log` (outside the install folder, not cleaned on uninstall).
- Uninstall registry entry: `HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\<packId>`: DisplayName=<packId>,
  `UninstallString` = `"...\Update.exe" --uninstall`, `QuietUninstallString` = `"...\Update.exe" --uninstall --silent`.
- Shortcuts: created by default in **both** locations: `...\Start Menu\Programs\<packId>.lnk` and `<Desktop>\<packId>.lnk`
  (Desktop may be OneDrive-redirected), both targeting `current\GhNotify.exe`. The name is the packId unless `--packTitle` is set.
  Choose locations at pack time with `vpk pack --shortcuts StartMenuRoot` (default `Desktop,StartMenuRoot`).
- Silent install does NOT launch the app afterwards.

## Silent install / update / uninstall commands

- **Silent install:** `<packId>-win-Setup.exe --silent` (exit 0, a few seconds). Other options: `-v/--verbose`, `-l/--log <FILE>`,
  `-t/--installto <DIR>`, `-- <exe args>`.
- **Update from a local folder, API (works).** Compiled against Velopack 1.2.161:
  ```csharp
  var mgr = new UpdateManager(new SimpleFileSource(new DirectoryInfo(dir)));  // SimpleFileSource(DirectoryInfo)
  UpdateInfo? info = await mgr.CheckForUpdatesAsync();                        // null when nothing newer
  await mgr.DownloadUpdatesAsync(info);                                       // (UpdateInfo, Action<int>? progress, CancellationToken)
  mgr.ApplyUpdatesAndRestart(info, new[] { "--after-update" });               // (VelopackAsset, string[]? restartArgs); process exits
  // or: mgr.WaitExitThenApplyUpdates(info, silent: true, restart: true, restartArgs: new[] { "--after-update" });
  //     (VelopackAsset, bool silent, bool restart, string[]? restartArgs); returns, the app must then exit itself
  // also: ApplyUpdatesAndExit(VelopackAsset)
  ```
  `info.TargetFullRelease.Version` reported the new version. Both Apply paths worked end to end (0.0.1 -> 0.0.2 via ApplyUpdatesAndRestart,
  0.0.3 -> 0.0.4 via WaitExitThenApplyUpdates); the app restarted on the new version with the restart args. Hook order:
  BeforeUpdate(old) -> AfterUpdate(new) -> Restarted(new). The old nupkg is removed from `packages\`. About 8-10 s from call to restarted app.
- **Update.exe CLI from a local package (works):**
  `%LocalAppData%\<packId>\Update.exe apply --package <path\to\<packId>-<ver>-full.nupkg> --norestart --silent` (exit 0).
  `apply` options: `--norestart`, `--waitPid <PID>`, `-p/--package <FILE>`, `-- <exe args>`. The source nupkg is not moved (and the previous nupkg stays in `packages\`).
  BeforeUpdate/AfterUpdate hooks ran. A bad package path retries ~3 s then exits 1.
  Other subcommands: `start [EXE_NAME] [--waitPid <PID>] [-- args]`, `patch --old --delta --output`, `uninstall`.
  Global flags: `--verbose`, `-s/--silent`, `--rootDir`, `--packageDir`, `-l/--log`.
- **Silent uninstall:** `%LocalAppData%\<packId>\Update.exe --uninstall --silent` (the registered QuietUninstallString; exit 0, no UI, done in ~5 s).
  `Update.exe uninstall --silent` is the subcommand form listed in `--help` (not exercised separately).
- **What uninstall deletes:** the ENTIRE `%LocalAppData%\<packId>\` folder (stub, Update.exe, current, packages), both shortcuts
  (Desktop and Start menu) and the Uninstall registry entry. Verified with extra files placed in the root: a `userdata\settings.json` and a
  `root.txt` created by hand next to `current\` were deleted too. **Consequence:** the real app keeps user data in `%LocalAppData%\GhNotify`,
  which would also be the Velopack install root for packId `GhNotify`, so uninstall (and any in-place reinstall that wipes the root) would delete
  user data unless it is moved outside that folder or the migration is handled. It left `%LocalAppData%\velopack\*.log` behind.

## Hook behaviour

API names that compile in 1.2.161 (all on `VelopackApp.Build()`, each takes a `VelopackHook` delegate, usable as `v => ...` with the version):
`OnAfterInstallFastCallback`, `OnAfterUpdateFastCallback`, `OnBeforeUpdateFastCallback`, `OnBeforeUninstallFastCallback`,
`OnFirstRun`, `OnRestarted`, finished with `.Run()`. Also `SetAutoApplyOnStartup(bool)`, `SetArgs`, `SetLocator`, `SetLogger`, `SetAppUserModelId`.
`UpdateManager.IsInstalled` (bool; True when run from the installed path), `UpdateManager.CurrentVersion` (installed version, e.g. `0.0.4`),
plus `AppId`, `IsUpdatePendingRestart`, `UpdatePendingRestart`. Constructors: `UpdateManager(IUpdateSource, UpdateOptions?, IVelopackLocator?)`,
`UpdateManager(string, UpdateOptions?, IVelopackLocator?)`, `UpdateManager(UpdateOptions, IVelopackLocator?)`.

Observed:
- `OnAfterInstallFastCallback` ran during the silent install (version 0.0.1) and **could write HKCU** (it created `HKCU\Software\GhNotifySpikeTest`),
  so writing the HKCU Run value there is possible. No Run key was written by the spike.
- `OnBeforeUninstallFastCallback` ran on uninstall (it deleted the HKCU test key), so it is the place to remove the Run value.
- `OnBeforeUpdateFastCallback` and `OnAfterUpdateFastCallback` ran for both the API and the CLI update paths. `OnRestarted` ran after a restart following an update.
- Hooks execute in their own short-lived process invocation of the app exe; code after `Run()` in `Main` is where normal startup continues in a normal launch.
- `OnFirstRun` was not seen in this flow (silent setup does not launch the app); do not rely on it. Register the Run key in `OnAfterInstallFastCallback`.

## mergeStateStatus result

Query: `search(query:"is:pr is:open author:@me", type:ISSUE, first:50){ issueCount nodes{ ... on PullRequest { reviewDecision mergeStateStatus mergeable isDraft } } }`.
- `mergeStateStatus` is returned by `gh api graphql` **without any preview header** (no error, real values).
- 6 open PRs. `mergeStateStatus`: CLEAN x2, BLOCKED x1, DIRTY x1, UNKNOWN x2.
- `mergeable`: MERGEABLE x3, CONFLICTING x1, UNKNOWN x2 (UNKNOWN is returned while GitHub computes it lazily; treat as "not yet known", re-poll later).
- `reviewDecision`: APPROVED x3, REVIEW_REQUIRED x1, null x2.
- Only CLEAN, BLOCKED, DIRTY and UNKNOWN were observed; other documented enum members (BEHIND, DRAFT, HAS_HOOKS, UNSTABLE) were not seen.

All tests passed (GhNotify.Tests 372, GhNotify.App.Tests 31).

| GhNotify.Tests (Core, GitHub, Ado, Agents) | 0.9515 | 1923 / 2021 |

- Combined by the agreed formula (sum covered / sum valid): 2058 / 5028 = **0.4093**; floor = floor(40.93) - 2 = **38**.
- Caveat: the App.Tests report also instruments the library projects, so the sum double counts lines. A line-level union of both reports
  (max hits per file+line) is 2053 / 3007 = **0.6827**, which would give a floor of 66. The libraries sit at ~95%; the App WPF code is almost untested.
